Researching app integrations with an evidence-driven agent.

A research pipeline that turns a 100-app integration research problem into a repeatable workflow: discover documentation, collect evidence, generate structured findings, and validate the output against a fixed schema.

Honest status: the research pipeline is implemented and has successfully produced validated results for the apps reached in the current run. I am not claiming a completed 100-app dataset or a verified accuracy percentage because those were not completed before submission.

At a glance

The important part is not scraping pages. It is creating a repeatable research process that can scale and preserve evidence instead of turning web research into unsupported guesses.

The product insight

The hard part of app integration research is not finding an API URL. It is determining whether an agent can actually use that API: authentication, credential access, API breadth, MCP availability, and approval barriers all matter.

That makes the output useful for prioritization rather than merely creating a directory of APIs.

Why Ollama?

The original implementation used the OpenAI API. During development, the API returned an insufficient quota error.

Rather than stop the project, I moved the OpenAI-compatible client to a local Ollama endpoint. 

client = OpenAI(
    base_url="http://localhost:11434/v1",
    api_key="ollama"
)

model = "qwen3:1.7b"

This made the research agent runnable without a paid API account. The trade-off is model capability and inference latency.

Important limitation discovered:

The first Salesforce result shows why verification matters. The model returned a plausible buildability verdict while the available evidence did not establish every underlying field. The pipeline therefore should not treat model confidence as proof.

The intended next step is to run the verifier against fresh evidence and route uncertain claims to human review.

Evidence-first design

Official sources first

The research prompt explicitly prioritizes official developer, API and authentication documentation.

No invented URLs

The structured prompt requires evidence URLs to come from the supplied source set.

Unknown is allowed

When the supplied evidence cannot support a claim, the model is instructed to return an unknown value rather than guess.

Verification strategy

Accuracy is the most important part of this problem. I designed a separate verification stage instead of assuming that a generated answer is correct.

Verification layer Status Purpose
Schema validation IMPLEMENTED Pydantic validates the generated object against the research schema.
Evidence constraints IMPLEMENTED Research prompts require claims to be supported by supplied sources.
Dedicated verifier IMPLEMENTED agent/verifier.py checks authentication, credentials, API surface, MCP, buildability and evidence quality.
100-app verification run NOT CLAIMED The complete run was not finished before submission.
Human spot-check accuracy NOT CLAIMED I do not report an accuracy percentage without actually performing the checks.

Where the human belongs

The goal is not to remove humans from the process completely. The goal is to make humans spend their time only where judgment adds value.

  • Conflicting official documentation
  • Unclear paid vs free credential requirements
  • Enterprise / partner approval gates
  • Official vs community MCP implementations
  • Pages that are inaccessible or dynamically rendered
  • Low-confidence or contradictory research

Everything else should be pushed through the automated pipeline.

What the completed dataset would answer

I intentionally do not fabricate aggregate findings from a partial run. These are the decision questions the final analysis is designed to answer.

01

Which auth method dominates?

OAuth2 vs API keys vs tokens vs other authentication.

02

Where are the gates?

Self-serve vs paid vs admin approval vs partner/contact-sales.

03

Where are the easy wins?

Public APIs with self-serve credentials and broad surfaces.

04

What blocks integrations?

Recurring approval, authentication, API or documentation barriers.

The pipeline uses an OpenAI-compatible client pointed at the local Ollama server, so an OpenAI API key is not required for the research stage.

If I had another iteration

1. Finish the batch

Run the complete 100-app dataset with retries and persist failures instead of stopping the entire pipeline when one app fails.

2. Strengthen evidence retrieval

Prefer direct developer documentation over generic marketing pages and add better handling for JavaScript-heavy documentation sites.

3. Close the verification loop

Run the verifier on every result, calculate field-level accuracy on a manually checked sample, and record every correction.

4. Turn findings into prioritization

Create an easy-win score combining API breadth, credential access, authentication complexity and integration blockers.

Takeaway

I treated the assignment as an operations problem, not a scraping problem: automate the repeatable research, preserve the evidence, validate the structure, and make uncertainty visible.

The current implementation demonstrates the research loop and has produced real structured output. I have intentionally separated what is implemented from what still requires a complete batch run and human verification.
